## Overview

This Concept Design Document describes the conceptual architecture and high-level
design approach for the Customer Loyalty Program. It bridges business requirements
with the technical solution.

## Design Philosophy

The loyalty system will be implemented as a standalone microservice with an
event-driven architecture, consuming purchase events from the existing Kafka bus
and exposing a REST API for frontend consumption.

## Concept Components

### C-01
**Title:** Loyalty Core Service
**Priority:** High
**Status:** Approved
**Description:** A dedicated microservice responsible for managing member enrolment,
tier calculation, points accrual, and redemption. The service will expose REST APIs
consumed by web, mobile, and in-store channels.
**Acceptance Criteria:**
- AC-01: Service deployed as independent Kubernetes pod
- AC-02: REST API follows OpenAPI 3.0 specification
- AC-03: All events published to Kafka topic loyalty.events
**Traces To:** BRD-001/R-01, BRD-001/R-04

### C-02
**Title:** Tier Engine
**Priority:** High
**Status:** Approved
**Description:** A rules engine embedded in the Loyalty Core Service that calculates
and assigns membership tiers based on cumulative points. Tier upgrades trigger
automated notifications via the Notification Service.
**Acceptance Criteria:**
- AC-01: Tier recalculated on every points accrual event
- AC-02: Tier downgrade evaluated on a nightly batch job
- AC-03: Tier change event published to Kafka for downstream consumers
**Traces To:** BRD-001/R-02

### C-03
**Title:** Redemption Gateway
**Priority:** High
**Status:** Approved
**Description:** Integration component between the Loyalty Core Service and the
Payment Gateway. Handles atomic redemption transactions ensuring points are
deducted only on successful payment confirmation.
**Acceptance Criteria:**
- AC-01: Redemption uses distributed transaction pattern (2-phase commit or saga)
- AC-02: Failed redemption rolls back points deduction automatically
- AC-03: Redemption confirmation sent to Notification Service within 30 seconds
**Traces To:** BRD-001/R-05

### C-04
**Title:** Web and Mobile Frontend Integration
**Priority:** Medium
**Status:** Approved
**Description:** Frontend integration pattern for the customer loyalty dashboard
on web (React) and mobile (React Native). The dashboard will consume the Loyalty
Core Service REST API via an API Gateway.
**Acceptance Criteria:**
- AC-01: Dashboard data refreshed on page load and every 5 minutes
- AC-02: Mobile app fetches data on app foreground event
- AC-03: API Gateway rate limit: 100 requests per customer per minute
**Traces To:** BRD-001/R-06

### C-05
**Title:** Notification Integration
**Priority:** Medium
**Status:** Approved
**Description:** The Loyalty Core Service will publish notification events to the
existing Notification Service for all customer-facing communications including
enrolment confirmation, tier upgrade, and point milestone alerts.
**Acceptance Criteria:**
- AC-01: Notification events published within 5 seconds of triggering action
- AC-02: Notification Service handles retry on delivery failure
- AC-03: Customer notification preferences respected
**Traces To:** BRD-001/R-03

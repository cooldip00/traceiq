## Overview

This Solution Design Document details the technical solution for the Customer
Loyalty Program. It is written against BRD v1.0 requirements.

## SEEDED CONFLICT: This SDD references BRD v1.0 but the current BRD version is 1.2.
## The structural validator will detect this version mismatch.

## Architecture Overview

The solution comprises three new components deployed in the existing Kubernetes cluster:

1. **Loyalty Service** — Core business logic microservice (Node.js / Express)
2. **Loyalty DB** — PostgreSQL database for member profiles and transaction history
3. **Loyalty Admin** — Internal React admin panel for marketing team configuration

## Solution Components

### S-01
**Title:** Loyalty Service API Design
**Priority:** High
**Status:** Approved
**Description:** RESTful API exposing endpoints for enrolment, points query,
redemption, and tier status. All endpoints secured with OAuth 2.0 bearer tokens.
The service will consume purchase events from Kafka topic order.completed.
**Acceptance Criteria:**
- AC-01: API documented in OpenAPI 3.0 format
- AC-02: All endpoints return JSON with consistent error schema
- AC-03: P95 response time < 200ms under 1000 concurrent users
**Traces To:** CDD-001/C-01

### S-02
**Title:** Database Schema Design
**Priority:** High
**Status:** Approved
**Description:** PostgreSQL schema for the loyalty domain including members,
point_transactions, tier_history, and reward_redemptions tables.
Partitioned by customer_id for horizontal scaling.
**Acceptance Criteria:**
- AC-01: Schema migrations managed via Flyway
- AC-02: Read replicas configured for dashboard query load
- AC-03: PII fields encrypted at rest (AES-256)
**Traces To:** CDD-001/C-01

### S-03
**Title:** Points Accrual Event Consumer
**Priority:** High
**Status:** Approved
**Description:** Kafka consumer group subscribing to order.completed events.
Processes idempotent point accrual using order_id as deduplication key.
Points calculation runs synchronously; result published to loyalty.events topic.
**Acceptance Criteria:**
- AC-01: Consumer group lag monitored via Datadog dashboard
- AC-02: Idempotency guaranteed using order_id unique constraint in DB
- AC-03: Dead letter queue configured for malformed events
**Traces To:** CDD-001/C-01, CDD-001/C-02

### S-04
**Title:** Redemption Saga Implementation
**Priority:** High
**Status:** Approved
**Description:** Implements the saga pattern for atomic redemption transactions.
Step 1: Reserve points. Step 2: Confirm payment. Step 3: Deduct points.
Compensation transaction rolls back point reservation on payment failure.
**Acceptance Criteria:**
- AC-01: Saga state persisted to loyalty_sagas table
- AC-02: Compensation triggered automatically on payment timeout (30s)
- AC-03: Redemption idempotent using checkout_session_id
**Traces To:** CDD-001/C-03
